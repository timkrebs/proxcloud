# Proxcloud Security Audit — Findings Register (2026-08-14)

**Branch:** `security/hardening-pass` · **Base:** `731dcfa` · **Status:** REMEDIATION REQUIRED (final security-reviewer PASS pending)

> **Remediation update (2026-09-24, `w1-security-hardening`):** the review of
> the first hardening pass found the H2/H3 remediation broken in the real
> tunnel topology (spoofable X-Real-IP through Caddy; one shared IP bucket for
> all users) and gaps in H5 (check-then-act, rollback and per-disk deltas
> ungated) and H6 (VMID-reuse leak). A second remediation round closed those;
> its re-review then found four more blockers in that remediation (H-A–H-C,
> M-1 in **Second review round** below), closed by a third round. The
> per-finding status notes below describe the code as it now stands (see also
> ADR-0034); still-open items are in **Open residuals (2026-09-24)** at the end.

Proxcloud is now publicly reachable via Cloudflare Tunnel at `portal.proxcloud.io` (prod) and
`portal.staging.proxcloud.io` (staging). This audit assumes the origin is directly reachable (LAN /
tunnel-bypass) and that every guarantee must hold at the application layer.

**Infra facts confirmed with the operator (2026-08-14):**
- Cloudflare Access is **not** enabled → we ADR a recommendation; all app controls must hold standalone.
- **No** edge WAF / rate-limiting → the app is the only line of defense (fail-safe sizing).
- API is **same-origin** (Next proxies `/api/*`) → CORS effectively same-origin, CSP `connect-src 'self'`
  (+ the `wss://` console origin), Host allowlist = the two portal hosts + internal names.

**Method:** 8 read-only security-reviewer agents swept the scope categories in parallel (SQL/Proxmox/shell
injection, authN/session, authZ/tenant-boundary, CORS/CSRF/headers, input-validation, secrets/exposure,
transport/infra/deps, business-logic), plus `govulncheck`, `npm audit`, and `gitleaks` over full history.
Findings below are the consolidated, de-duplicated, severity-ordered register. Each fix ships with a
regression test that fails-before / passes-after; nothing merges to `main` without a final PASS.

## Controls verified SOUND — do NOT "fix" or weaken these

The following are correctly implemented and their tests must keep passing through this pass:

- **Injection:** every SQL query is pgx-parameterized (`store/*.go`); the one dynamic query (`ListAudit`)
  only `fmt.Sprintf`s placeholder indices, never user values, with a fixed-literal `ORDER BY`. Proxmox paths
  `url.PathEscape` every segment; node/storage/pool/bridge pass `ValidPVEID`; VMIDs are int-range-checked;
  type/action/timeframe are allowlisted; no `exec.Command`; SSH forced-command wrappers reject globbing/eval.
- **Tenant boundary (IDOR):** `ResolveTenant→ResolveScope→Enforce→AuditOnMutation` runs before every handler
  and before any Proxmox call; `ResolveOwnership`/`ResolveOwnershipForTask` filter by `tenant_id` → **404 not
  403**; the non-`{vmid}` cases (deployments, tasks, invitations, body `projectId`, clone-source) all carry an
  explicit tenant re-check.
- **Permission-table completeness:** `permissions_test.go` walks the real router and fails CI on any
  unregistered/stale route — no endpoint ships unauthenticated by omission.
- **Roles:** `EffectiveRole = max(tenant, project)` (project role only adds); Reader cannot reach any mutating
  verb; platform-admin surface separately gated and unreachable by a tenant Owner.
- **Quota race:** `ReserveOwnership` holds a per-tenant `pg_advisory_xact_lock` over both project+tenant caps
  in one tx with no PVE call under the lock — concurrent creates cannot bypass the cap **at create time**.
- **Session/creds:** opaque 256-bit tokens stored SHA-256-hashed, rotated on login/privilege-change, revoked
  server-side on logout; Argon2id 64 MiB/t=3/p=2; TOTP AES-256-GCM sealed; recovery codes + login challenges
  single-use; invitation tokens hash-only, single-use, expiring, role bound in the DB row (not the token).
- **Console proxy:** ticket minted only after the ownership-checked POST, single-use 25s TTL, never in the
  browser URL; WS `CheckOrigin` exact `FrontendOrigin` match; `maxBridges=8`.
- **Secrets at rest:** gitleaks clean over all history; `.env` gitignored; Proxmox token never logged; no PAT
  surface exists.

## HIGH

### H1 — No security-header middleware (CSP / HSTS / X-Frame-Options / nosniff / Permissions-Policy)
*Confidence: confirmed · Owner: frontend-engineer (Next headers) + backend-engineer (API middleware) + architect (CSP ADR) · merged from CORS-High + Transport-Med*

- **Attack:** portal HTML ships with no `frame-ancestors`/`X-Frame-Options` → any page can iframe the portal
  and clickjack destructive actions (VM delete, invite accept) from an authenticated victim. No CSP → any
  reflected/stored XSS or one compromised frontend dep runs with full privilege and exfiltrates anywhere
  (`connect-src` unrestricted) on an app holding an infra-destroying Proxmox token. No HSTS at the origin →
  LAN-MITM/tunnel-bypass downgrade strips the Secure cookie. No `nosniff` → MIME sniffing of API responses.
- **Location:** `frontend/next.config.ts:21-31` (only Referrer-Policy on `/invite`); `backend/internal/httpserver/router.go:64-78` (no header middleware).
- **Fix:** global `next.config.ts` `headers()` for `/(.*)`: HSTS (`max-age=63072000; includeSubDomains; preload`),
  CSP (`default-src 'self'; script-src 'self'; style-src 'self'; connect-src 'self' <wss console origin>;
  frame-ancestors 'none'; base-uri 'none'; object-src 'none'; form-action 'self'`), `X-Content-Type-Options:
  nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin` (keep `no-referrer` on
  `/invite`), `Permissions-Policy: camera=(), microphone=(), geolocation=()`. Add a backend middleware so
  direct-origin API/WS responses also carry `nosniff` + HSTS + CSP `frame-ancestors 'none'`. **ADR the CSP.**
- **Test:** integration test asserts `GET /` and `GET /api/health` return CSP with `frame-ancestors 'none'`,
  `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, HSTS — absent today.

### H2 — Brute-force bypass: RealIP trusts spoofable X-Real-IP/X-Forwarded-For, and no per-account lockout
*Confidence: confirmed · Owner: backend-engineer + architect (trusted-proxy ADR) · merged from AuthN-High + Transport-Med; also closes AuthN-Low X-Forwarded-Proto downgrade (L→folded)*

- **Attack:** `middleware.RealIP` is mounted unconditionally and overwrites `RemoteAddr` from the
  client-supplied `X-Real-IP`/`X-Forwarded-For` with no trusted-proxy allowlist; Caddy sets `X-Forwarded-Proto`
  but never strips `X-Real-IP`. Reaching the origin off-proxy (LAN/tunnel-bypass, per threat model) an attacker
  rotates the header per request so each login/TOTP/invite attempt looks like a new IP → the 5/min per-IP
  window (the *only* brute-force control, no edge WAF) never trips → unlimited credential brute-force against
  any account incl. the platform admin. **Same root cause** lets `X-Forwarded-Proto: http` downgrade the
  Secure cookie when hit directly (`session.go` `secureFor`).
- **Location:** `router.go:74`; `auth/ratelimit.go:85-91` (`clientIP`); `session.go:87-102` (`secureFor`); Caddy
  `blue.caddy`/`green.caddy` (no `X-Real-IP` reset); `auth/handlers.go:181-216` (no per-account lockout).
- **Fix:** gate proxy-header trust behind `TrustProxyHeaders` **and** an explicit trusted-proxy CIDR (the Caddy /
  docker-edge source); off-proxy, key the limiter off raw TCP `RemoteAddr` and derive Secure from `r.TLS`/base
  (fail-safe Secure) — never client headers. Configure Caddy to reset `X-Forwarded-For`/`X-Real-IP` to the true
  client. Add a DB-backed **per-account** failed-login counter with exponential backoff/temporary lock,
  independent of the IP limiter.
- **Test:** 20 wrong-password logins each with a *different* `X-Real-IP` from an untrusted `RemoteAddr` → 6th+
  returns 429 (currently 401 forever). 20 failed logins for one email from 20 IPs → account backs off (429/423).

> **Status (2026-09-24): CLOSED with this remediation** (ADR-0034). The first
> pass gated the headers behind `TRUSTED_PROXY_CIDRS` but still copied a
> client-suppliable `X-Real-IP` (Caddy did not overwrite it) unvalidated into
> `RemoteAddr`. Now: Caddy ALWAYS overwrites `X-Real-IP` with `{client_ip}`,
> on the frontend route as well as `/api` and bare `/api`; on prod,
> `{client_ip}` comes from `CF-Connecting-IP` only for the pinned edge gateway
> (`10.254.254.1`, the source host cloudflared arrives from — H-C below); the
> backend reads ONLY `X-Real-IP`, only from its trusted peer (prod: Caddy's
> pinned `10.254.254.10/32`), and only when it `net.ParseIP`s — never
> `X-Forwarded-For` — else keeps the peer. Per-account lockout: email keys are
> SHA-256 (≤254-byte emails only), a failure streak decays after 2 h without
> failures (far longer than the 15-min max lock, so each expiry buys one guess,
> not a fresh set), locked or at-threshold entries are never evicted (M-1
> below), maps are hard-capped at 10k, and per-IP windows key IPv6 by /64. A
> per-account second-factor counter that a correct password does NOT reset
> (10 failures → 2FA step locked 15 min) closes the known-password TOTP grind;
> each attempt is reserved atomically with the lock check, and lock engagement
> plus the first refusal of each lock are audited. In-memory per instance —
> accepted residual, see Open residuals. Tests: `TestForwardedIPValidation`,
> `TestTrustedProxyHeaders`, `TestAccountLockoutDecays`,
> `TestAccountMapBounded`, `TestLockEvictionNeverUnlocks`,
> `TestLockoutRelocksAfterExpiry`, `TestSecondFactorCounterSurvivesPasswordSuccess`,
> `TestSecondFactorReserveIsAtomic`, `TestSecondFactorVerdictAuditSignals`,
> `TestSecondFactorLockoutAcrossChallenges`, `TestLoginLimiterIPv6SharesWindow`,
> `TestLoginRejectsOversizeEmail`.

### H3 — No global/per-tenant request rate limit and no Proxmox concurrency cap
*Confidence: confirmed · Owner: backend-engineer · Transport-High*

- **Attack:** only login/bootstrap/TOTP/invite are limited. Every other authenticated route proxies
  synchronously to Proxmox with no limit and no bounded semaphore. With no edge WAF, one authenticated tenant
  issuing many concurrent requests saturates the effectively-serialized Proxmox API and the Postgres pool →
  DoS of all tenants + stalled real infra ops. Create/delete also spawn one unbounded goroutine per `Submit`
  and retain every run in an in-memory map with no eviction.
- **Location:** `router.go:64-79`; handlers + `proxmox/gopve.go` (no PVE concurrency bound); `deploy/engine.go:110-116`.
- **Fix:** global token-bucket middleware keyed on session/tenant; a bounded semaphore wrapping `proxmox.Client`
  so total in-flight PVE calls are capped; stricter per-tenant limits on create/delete + cap concurrent
  in-flight deployments; evict finished runs from `Engine.runs`.
- **Test:** fire N+1 req/s at a mock-PVE read route from one session → beyond budget returns 429; assert ≤K
  simultaneous `proxmox.Client` calls under a burst.

> **Status (2026-09-24): CLOSED with this remediation** (ADR-0034). The first
> pass added the 600/min limiter and the PVE semaphore + SSE per-user cap, but
> keyed the limiter per IP — in the tunnel topology every user shares
> cloudflared's IP, so honest users shared ONE bucket and an unauthenticated
> flood could 429 the whole portal (and login for everyone). Now: a session
> whose cookie `Authenticate` has accepted draws from its own bucket (a
> bounded set of validated cookie hashes, filled by middleware mounted
> directly after `Authenticate`); every other request — including a made-up
> cookie value — draws from its client IP's bucket (IPv6 by /64). Buckets are
> O(1) fixed-window counters in a hard-capped map, swept at most every 10 s.
> Only `/api/health` + `/api/v1/version` are exempt; the streaming routes
> COUNT at open while staying exempt from body-cap/timeout. Tests:
> `TestRateLimitSessionAndIPBuckets`, `TestRandomCookiesShareIPBucket`,
> `TestLimiterStaysBounded`, `TestRouterMarksOnlyAuthenticatedSessions`,
> `TestRouterHealthNeverRateLimited`. Residuals (open, below): per-tenant
> fairness of the Proxmox semaphore slots and a hard cap on in-flight
> deployments.

### H4 — No request-body size limit on any route (incl. unauthenticated login/bootstrap/invite/TOTP)
*Confidence: confirmed · Owner: backend-engineer · Input-Validation-High*

- **Attack:** every handler does `json.NewDecoder(r.Body).Decode` with no bound; no `MaxBytesReader`, no
  `http.Server` body cap. An unauthenticated attacker POSTs arbitrarily large bodies to public endpoints — and
  `Login` decodes the body *before* `Limiter.Allow` — buffering them into memory before any auth/rate check →
  a few concurrent large bodies OOM the backend. Amplifier: passwords have a 12-char minimum but **no maximum**,
  so an unbounded password is fed to Argon2id/bcrypt.
- **Location:** `router.go:64-78`; `main.go:268-283`; decodes e.g. `auth/handlers.go:116,183`.
- **Fix:** global middleware wrapping `r.Body` in `http.MaxBytesReader` (~64–256 KiB) before decode, exempting
  only `/api/events` + `/api/console/ws/`; cap password length (reject >1024 bytes) before hashing; move
  `Limiter.Allow` ahead of the body decode in `Login`.
- **Test:** `POST /api/auth/login` with a 10 MB body → 413 and the handler never decodes/hashes; normal body still 200.

### H5 — Quota enforced only at create; disk-resize & config-update grow a guest past caps
*Confidence: confirmed · Owner: backend-engineer · Business-logic-High*

- **Attack:** the only quota gate is `ReserveOwnership` in `CreateGuest`. `UpdateGuestConfig` (cores/memory)
  and `ResizeGuestDisk` (disk) do **no** quota check and have no upper bound. A Contributor: create tiny guest
  (passes), then PATCH `config {cores:128, memory:1048576}` and POST `resize {sizeGib:100000}` → consumes
  vCPU/RAM/disk far beyond caps → cluster-wide exhaustion / co-tenant DoS. `ComputeUsage` then reports OVER
  quota, proving the bypass, yet the mutation was allowed.
- **Location:** `handlers/guest_detail.go:93-160` (config), `:211-237` (resize); gate only at `create.go:136` / `store/quota.go:190-238`.
- **Fix:** before applying a config-grow or disk-grow, compute the delta vs. current allocation and run it
  through the same per-tenant advisory-locked quota check (a "reserve delta" store op); reject `409
  quota_exceeded` when usage+delta exceeds project/tenant cap; add sane upper bounds; shrinks need no check.
- **Test:** tenant at cap N — PATCH raising cores/memory and POST resize growing disk beyond N each return 409
  (currently 200/202).

> **Status (2026-09-24): remediation hardened.** The first pass's
> `CheckGuestGrowth` was check-then-act (the advisory lock was released before
> Proxmox applied anything — N guests could grow into the same headroom),
> snapshot ROLLBACK was ungated, and the resize delta was measured against the
> boot-disk `maxdisk` (a non-boot-disk grow below the boot size looked like a
> shrink and bypassed quota). Now: `ReserveGuestGrowth` measures every charge
> against the guest's effective footprint max(live, stored reservation) and
> persists effective + charge on the ownership row IN the locked transaction,
> monotonically (a reservation can never go down); `ComputeUsage` counts
> active rows at max(live, reserved) — closing the race AND audit L4's
> snapshot-lag under-count for grown dimensions. vCPU/RAM targets are
> absolute (vCPU = sockets × cores, the unit quota counts); a disk resize is an
> additive delta measured against the NAMED disk's own `size=` and charged in
> full (H-A below). Rollback is gated through the same reservation using the
> snapshot's stored sizing, and fails closed when that sizing cannot be read.
> Tests: `TestGrowthReservationVisibleToCreate`, `TestConcurrentGrowsOneWins`,
> `TestRollbackOverQuotaBlocked`, `TestRollbackFailsClosed`,
> `TestRollbackUnlimitedContainerRefused`, `TestResizePerDiskDelta`,
> `TestResizeRepeatedDataDiskGrowIsCharged`, `TestReservationNeverLowered`,
> `TestConfigGrowChargesSockets`, `TestGrowthMath`, `TestNamedDiskSizeGiB`,
> integration `TestReserveGuestGrowthRaceRespectsCap` and
> `TestGrowthReservationMonotonicSQL`. Residuals (open, below): non-boot disks
> are not counted in `ComputeUsage` totals, and a reservation is never
> cleared after a shrink.

### H6 — Cross-tenant leak: `GET /api/notifications` serves the process-global task ring to every tenant
*Confidence: confirmed · Owner: backend-engineer · merged from Input-Validation-High + AuthZ-Med — **tenancy iron rule #1 violation***

- **Attack:** an authenticated-but-hostile tenant polls `GET /api/notifications` and receives the entire
  process-wide notification ring — every Proxcloud-initiated task across ALL tenants: guest names, VMIDs, node
  names, actions/outcomes, verbatim PVE exit strings → continuous cross-tenant surveillance. `POST
  /api/notifications/read` lets one tenant flip another tenant's notification Read flags (cross-tenant
  tampering). The SSE feed is correctly tenant-scoped; this REST sibling was not.
- **Location:** `handlers/notifications.go:12-31`; `tasks/registry.go:37-46,167-188` (no tenant field); mounted
  tenant-agnostically at `handlers.go:72-73`.
- **Fix:** tag each `Tracked`/`Notification` with the owning `tenantID` at `Track()` (carry it from the
  CreateContext/ownership row on the mutating path); filter `Notifications()`/`MarkRead()` by the caller's
  `ActiveTenantID` (platform-admin bypasses), mirroring `events/handler.go deliver()`; `MarkRead` only accepts
  IDs in the caller's tenant.
- **Test:** tenant A triggers a tracked task (VMID 100); `GET /api/notifications` as B returns `[]`, as A
  returns it; B cannot flip A's `Read`.

> **Status (2026-09-24): remediation hardened.** The first pass filtered the
> ring by the caller's LIVE owned-VMID set — but VMIDs are caller-chosen and
> reissued after a tombstone, so a tenant claiming a freed VMID inherited the
> previous owner's history (guest names, verbatim PVE errors). Now every
> entry stores the OWNING tenant at `Track()` time (deploy CreateContext,
> handler resolved scope, lifecycle ownership row); `Notifications`/`MarkRead`
> compare that stored tenant (admin sees all; no active tenant sees nothing);
> and the tombstone choke-points (user delete, TTL delete, set-member destroy)
> call `Registry.DropVMID`, so a tombstoned VMID carries nothing forward. A
> VMID freed by a released (failed) create is not dropped, but its entries stay
> invisible to every other tenant through the stored-tenant filter. The same
> VMID-reuse class remains OPEN on the task surfaces — see M-2 below.
> Tests: `TestRegistryNotificationsScopedToTenant`,
> `TestRegistryVMIDReuseDoesNotLeak`, `TestNotificationsScopedToTenant`.

## MEDIUM

### M1 — No Host-header allowlist (backend + prod Caddy `:80` accept any Host)
*confirmed · Owner: backend-engineer + release-engineer (Caddy) · CORS-Med* — DNS-rebinding / host-injection reach into the internal API.
**Fix:** backend middleware rejecting (421/404) any Host not in {2 portal hosts, internal compose names, localhost}, config-driven; and/or explicit Caddy host blocks. **Test:** `Host: attacker.example` → 421/404.

### M2 — `http.Server` sets only `ReadHeaderTimeout` (no Read/Write/Idle timeouts)
*confirmed · Owner: backend-engineer · merged Input-Validation-Med + Transport-Low* — slow-loris body/connection exhaustion.
**Fix:** set `ReadTimeout`, `WriteTimeout`, `IdleTimeout`, `MaxHeaderBytes`; keep SSE/WS on their long-lived path. **Test:** partial-body connection is closed within `ReadTimeout`.

### M3 — SSE `/api/events` has no per-user connection cap + per-connection 5s DB poll
*likely · Owner: backend-engineer · merged Transport-Med + Input-Validation-Med* — one tenant opening many streams → per-5s DB query storm starving the pgx pool; unbounded goroutines.
**Fix:** cap concurrent SSE subscribers per session/user (429/503 past cap); coalesce the owned-VMID query to one refresher per tenant; set explicit `pgxpool MaxConns`. **Test:** N+1 connections → last rejected; `ListOwnershipByTenant` called ≤once/tenant/interval.

### M4 — Go toolchain 1.26.5: 6 call-reachable stdlib DoS vulns (fixed in 1.26.6)
*confirmed · Owner: release-engineer/devops · merged Transport-Med + Input-Validation-Low* — `govulncheck` traces reachable `net/url`, `net/http` (pre-handshake slowloris on the public listener), `crypto/tls`, `encoding/xml`, `encoding/asn1`, `idna`.
**Fix:** bump build/CI toolchain to go1.26.6+, rebuild, re-run `govulncheck` to green; **wire `govulncheck` into CI as a gate.** **Test:** CI `govulncheck ./...` exits 0.

### M5 — `npm audit`: 3 high vulns (sharp/libvips runtime, postcss build-time) via next 15.5.23
*confirmed · Owner: frontend-engineer · Transport-Med*
**Fix:** `overrides` pinning `sharp>=0.35.0` and `postcss>8.5.22` (or upgrade Next, validate App-Router migration); triage sharp reachability (next/image). Wire `npm audit --omit=dev --audit-level=high` into CI. **Test:** CI audit clean; build + next/image still function.

### M6 — Cross-tenant enumeration via tenant catalog storage-`content` (unrestricted filter)
*likely · Owner: backend-engineer · AuthZ-Med — **iron rule #1***
- **Attack:** `GET /api/tenants/{t}/catalog/nodes/{node}/storages/{storage}/content` (Contributor) forwards the
  caller's `content` param verbatim to Proxmox. A hostile Contributor requests `content=images`/`backup` and
  enumerates all volumes on shared storage — other tenants' VMIDs, disk sizes, backup filenames.
- **Location:** `handlers/nodes.go:182-199`; tenant route `permissions.go:155` (admin copy correctly gated).
- **Fix:** on the tenant path, allowlist `content` to `{iso, vztmpl}`, reject else 400; keep the unrestricted variant admin-only. **Test:** Contributor with `content=images` → 400; `content=iso` → 200.

### M7 — Production silently falls back to `LogMailer`, printing raw single-use invite tokens to stdout/logs
*likely · Owner: backend-engineer · Secrets-Med — violates ADR-0013 §5.1*
**Fix:** fail-closed — in `config.Load`, when `!Dev` require `SMTP_HOST` (or explicit `PROXCLOUD_ALLOW_LOG_MAILER=true`); never select `LogMailer` in prod. **Test:** `config.Load` with `PROXCLOUD_ENV=production` + no `SMTP_HOST` → error; main-wiring asserts `*SMTPMailer` when `!Dev`.

### M8 — Snapshot storage is never counted against the disk quota
*needs-verification · Owner: backend-engineer · Business-logic-Med* — a Contributor repeatedly snapshots (esp. vmstate) to consume storage past the disk cap.
**Fix:** account snapshot/backup size against the disk quota, or cap snapshot count+size per project; reject a vmstate snapshot exceeding remaining quota. **Test:** at disk quota, a quota-exceeding vmstate snapshot is rejected/counted.

### M9 — No per-tenant node/storage allowlist (placement isolation)
*needs-verification · Owner: architect (decide) + backend-engineer · Business-logic-Med* — node/storage are fully tenant-chosen; a Contributor can concentrate their (quota-bounded) disk on premium/foreign storage (noisy-neighbor). Not a total-quota bypass.
**Fix:** bind an allowlist of permitted nodes/storages per tenant/project and validate create + scope the catalog; **or** ADR an explicit risk-acceptance for cluster-wide placement on the public topology. **Test:** create targeting a non-allowlisted node/storage → 404/400.

## Second review round (2026-09-24)

The re-review of the remediation above returned FAIL with four blockers, each
reproduced with a proof of concept. All are CLOSED; each new regression test
was checked to fail at the attack step against the pre-fix code where the fix
changed behavior.

- **H-A — Disk quota bypass by repeated per-disk resizes (HIGH) — CLOSED.**
  The resize handler built an ABSOLUTE disk target from the boot disk's live
  size, so every grow of the same data disk computed the same target and only
  the first was charged; the reservation was written as max(live, target), so
  a later boot-disk grow LOWERED it (cap 45 GiB → 105 GiB provisioned). A disk
  grow is now an additive delta charged on top of the effective footprint, and
  reservations are monotonic in SQL (`GREATEST`). Same round: vCPU targets are
  sockets × cores on config updates too (adopted multi-socket VMs were
  under-charged), rollback fails closed on unreadable sizing (L-7), and the
  growth pre-read is a tenant-filtered query (L-8). Commit `2bc3f59`.
- **H-B — Random cookies bypass the global limit and grow it unbounded
  (HIGH) — CLOSED.** Any cookie value earned its own bucket (60,000 requests
  from one IP, zero 429s) and past 8192 keys every request scanned the whole
  map. Only sessions `Authenticate` has accepted now earn a bucket; the map is
  hard-capped with amortized sweeps. Same round: `X-Forwarded-For` is never
  consulted (L-5). Commit `fa704c4`.
- **H-C — Prod Caddy trust could never match the Docker topology (HIGH) —
  CLOSED.** Host cloudflared arrives at Caddy from the edge network's gateway,
  never from loopback, on a Docker-assigned subnet no setting could name — so
  all anonymous users shared one bucket. The edge network now has pinned
  addressing (created only by `bin/ensure-networks.sh`, which makes deploys
  refuse before touching a container until the one-time migration in
  `docs/runbooks/prod-edge-network-migration.md` is done); Caddy is pinned at
  `10.254.254.10`, published on `127.0.0.1:80` only (tunnel-only), trusts
  `CF-Connecting-IP` only from the gateway, and the backend trusts only
  Caddy's /32. Commit `dbfd4fd`.
- **M-1 — Lock-eviction flooding unlocked accounts (MEDIUM) — CLOSED.** The
  hard-cap eviction preferred the victim's lock. Locked or at-threshold
  entries are never evicted; a map full of them refuses new keys instead.
  Same round: atomic 2FA attempt reservation (L-1), audited 2FA locks (L-2),
  2 h failure decay (L-3), IPv6 /64 limiter keys. Commit `682810b`.
- **M-2 — VMID-reuse history leak on the task surfaces (MEDIUM) — OPEN.**
  Pre-existing and outside this pass: `ListTenantTasks`, `GetTenantTask` and
  `GetTenantTaskLog` (and the activity overlay) authorize a UPID by its VMID's
  CURRENT owner, so a tenant that claims a freed VMID can read the previous
  owner's Proxmox tasks, exit text and logs. Fix: a `claimed_at` watermark on
  ownership (set on insert and on revival) and only surface tasks started at
  or after it. Tracked as R6 below.

## Open residuals (2026-09-24 review of the hardening pass)

Explicitly OPEN items from the security review of `w1-security-hardening` —
accepted for this merge, tracked here so the register stays honest:

- **R1 — Per-tenant Proxmox-slot fairness.** The PVE concurrency semaphore is
  a single global pool: one tenant's burst can occupy every slot and starve
  other tenants' Proxmox calls (a fairness gap, not a bypass — the global rate
  limit bounds the burst). Needs per-tenant sub-budgets or a fair queue.
- **R2 — Hard cap on in-flight deployments.** `Engine.Submit` spawns one
  goroutine per deployment with no ceiling on concurrent in-flight runs
  (finished runs are pruned, but in-flight count is unbounded below the
  global rate limit). Needs an explicit cap → 429/503 past it.
- **R3 — SSH-session cap (snippet writer).** Snippet delivery opens SSH/SFTP
  sessions to the PVE node without a concurrency bound of its own; a burst of
  catalog deploys can pile up sessions on the node. Needs a small semaphore
  around the writer.
- **R4 — Non-boot-disk usage accounting.** `ComputeUsage` counts a guest's
  disk as the boot-disk `maxdisk` from the cluster snapshot; additional disks
  are invisible to the USAGE total (their GROWTH is now correctly charged
  per-disk at resize time, and the grown footprint is reserved — but a guest
  created outside Proxcloud, or disks added out-of-band, under-count).
- **R5 — DB-backed login/2FA lockout.** All limiter/lockout state (per-IP
  windows, account lockout, second-factor counter, global throttle) is
  in-memory per backend instance — accepted for the single-active-color
  deployment (ADR-0034), reset on restart, multiplied by replica count if the
  topology ever scales out. The per-challenge attempt counter is already
  DB-backed. Needs a durable, multi-instance-safe lockout store. Related: a
  full account-lockout map (10k locked or at-threshold accounts) stops
  counting failures for NEW accounts rather than unlocking existing ones — the
  per-IP window still applies to them.
- **R6 — VMID-reuse leak on the task surfaces (M-2 above).** Needs the
  `claimed_at` ownership watermark.
- **R7 — `Registry.ActiveFor` is keyed by VMID only.** A task left running
  from a VMID's previous owner could surface its UPID (not its content) as the
  new owner's transitional status. Same fix family as R6.
- **R8 — Growth reservations are never cleared.** They are monotonic by
  design; after a shrink (or once Proxmox reflects a grow) a stale reservation
  keeps over-counting — the safe direction, but it can lock a tenant out of
  headroom it has freed. Needs a reconciler pass that clears a reservation once
  the guest's actual configuration is at or below it and no grow is in flight.
- **R9 — No owner notification on a second-factor lock.** The lock and its
  first refusal are audited, but the account owner is not told that someone
  holds their password. Needs a notification (email) on lock engagement.
- **R10 — No automated check that real client IPs reach the backend.** After
  the edge migration the runbook verifies it by hand (Settings → Sessions). A
  prod-smoke assertion that the smoke session's recorded IP is not an edge
  address would catch a future trust-chain regression.
- **R11 — Next's vendored postcss (build-time).** `npm audit` still reports
  the postcss HIGHs bundled inside `next`, fixable only by moving to a new
  `next` major. Not reachable at runtime.
- **Observation — authz ownership resolution compares tenants in Go.**
  `authz.ResolveOwnership` loads a row by VMID and compares its tenant in Go
  (correctly — a foreign row is a 404). Tenancy iron rule #1 asks for the
  tenant filter in the query itself, which the growth path now does
  (`GetLiveOwnershipForTenant`); moving the choke-point to the same pattern
  is a consistency follow-up, not a vulnerability.
