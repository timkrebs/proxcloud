# Proxmox VE cloud-init & guest provisioning semantics

Authoritative reference for how the Proxcloud backend delivers **cloud-init**
(and equivalent LXC provisioning) to guests for the service-catalog wave. It
defines the exact endpoints, parameters, override rules, readiness signal, and
the security-critical encoding of injected credentials.

- **Target version:** PVE **9.x** (the Proxcloud server runs **9.2.4**). Cloud-init
  mechanics (`cicustom`, the cloudinit drive, snippet storage) are stable across
  8.x/9.x; **the guest-agent privilege names changed in 9.x** and are flagged
  inline (§3, §5). Anything else version-sensitive is called out.
- **Scope:** documentation only. This file is the contract the backend codes
  against; it does not change application code.
- **Grounding in existing code:**
  - `backend/internal/deploy/params.go:222-252` — today's **inline** cloud-init
    for qemu: sets the generated drive `ide0=<storage>:cloudinit` plus `ciuser`,
    `cipassword`, `sshkeys` (URL-encoded), `ipconfig0`, `nameserver`,
    `searchdomain`. LXC branch (`:196-209`) sets native `password`,
    `ssh-public-keys`, `nameserver`, `searchdomain`.
  - `backend/internal/proxmox/guest_config.go:98-164` — `AgentInterfaces`: reads
    `GET .../agent/network-get-interfaces` (qemu) / `.../interfaces` (lxc) and
    maps "guest agent is not running" to `ErrAgentUnavailable` (a state, not a
    failure).
  - `deploy/terraform/main.tf:81-94` + `deploy/terraform/templates/cloud-init.yaml.tftpl`
    — prod delivers a **snippet** (`content_type = "snippets"`) that the `bpg`
    provider uploads **over SSH**, not via REST (see §1.3).
  - **Vendored `go-proxmox`** rejects the `snippets` storage content type: it has
    no REST path to upload a snippet body. Snippet placement is out-of-band
    (SSH/SFTP), by design (§1.3).

## 0. Endpoint & parameter summary

All paths are prefixed with `/api2/json`.

| Method | Path | Key params | Sync / async | Privilege (PVE 9.x) |
|--------|------|-----------|--------------|---------------------|
| POST | `/nodes/{node}/qemu` (create) | `ide0=<st>:cloudinit`, `cicustom`, `ipconfig0`, `nameserver`, `searchdomain`, `citype` | **async → UPID** | `VM.Allocate` (+ `Datastore.AllocateSpace`, `SDN.Use`) |
| PUT/POST | `/nodes/{node}/qemu/{vmid}/config` | `cicustom`, `ciuser`, `cipassword`, `sshkeys`, `ipconfig[n]`, `citype` | POST is **async → UPID**; PUT is **sync** | `VM.Config.Cloudinit` (any-of, see §3) |
| GET | `/nodes/{node}/qemu/{vmid}/agent/network-get-interfaces` | — | **sync** (agent RPC) | `VM.GuestAgent.Audit` **or** `.Unrestricted` |
| POST | `/nodes/{node}/qemu/{vmid}/agent/exec` | `command`, `input-data` | **sync** (returns `pid`) | `VM.GuestAgent.Unrestricted` |
| GET | `/nodes/{node}/qemu/{vmid}/agent/exec-status` | `pid` | **sync** (`exited`, `exitcode`, `out-data`) | `VM.GuestAgent.Unrestricted` |
| POST | `/nodes/{node}/lxc` (create) | `password`, `ssh-public-keys`, `nameserver`, `searchdomain` | **async → UPID** | `VM.Allocate` (+ `Datastore.AllocateSpace`) |

There is **no** REST endpoint to upload a cloud-init snippet body (§1.3).

## 1. VM (qemu) cloud-init via `cicustom`

### 1.1 What `cicustom` is

`cicustom` replaces PVE's auto-generated cloud-init files with files you supply.
API schema (`/nodes/{node}/qemu/{vmid}/config`, format `pve-qm-cicustom`):

> `cicustom`: "cloud-init: Specify custom files to replace the automatically
> generated ones at start."
> Format: `[meta=<volume>] [,network=<volume>] [,user=<volume>] [,vendor=<volume>]`

Each part is **independent**: `user=` replaces only the generated **user-data**;
`network=` replaces the generated **network-config**; `meta=` the **meta-data**;
`vendor=` the **vendor-data**. Any part you omit is still auto-generated by PVE
(Cloud-Init Support wiki; Thomas-Krenn "Custom Cloud Init Config"). So
`cicustom "user=<vol>"` gives you full control of user-data while PVE keeps
generating network-config from `ipconfig[n]` (§1.5).

The set command (wiki example, verbatim):

```
qm set 9000 --cicustom "user=local:snippets/userconfig.yaml"
```

The `<volume>` is a **storage volume-id in `snippets/` form**, not a bare path:
`<datastore>:snippets/<file>.yaml`.

### 1.2 The snippet must live on `snippets`-enabled storage

Cloud-Init Support wiki, verbatim:

> "The custom config files have to be on a storage that supports snippets and
> have to be available on all nodes the VM is going to be migrated to."

So the datastore holding the file must have the **`snippets`** content type
enabled (`pvesm set <storeid> --content snippets,...` or in the GUI). Thomas-Krenn
adds that for clusters the snippet should sit on shared storage (e.g. CephFS) so
the VM stays migratable. Proxcloud's server is single-node in v1; local
`snippets` content is sufficient, but pin the file to a datastore reachable from
the target node.

### 1.3 There is NO REST API to upload a snippet — it is placed out-of-band

**Confirmed:** the Cloud-Init Support wiki documents only the CLI/volume-id form;
there is no `/api2/json` endpoint that accepts a snippet **body**. The upload
path (`POST /nodes/{node}/storage/{storage}/upload`) accepts only `iso`,
`vztmpl`, and `import` content — **not `snippets`**. This is why:

- the vendored **`go-proxmox` rejects the `snippets` content type** (no REST
  upload helper), and
- prod's Terraform (`deploy/terraform/main.tf:81-94`) uses
  `proxmox_virtual_environment_file { content_type = "snippets" }`, which the
  **`bpg` provider writes over SSH/SFTP** to the datastore's `snippets/`
  directory (hence the provider's `ssh` block).

**Implication for the backend:** to use `cicustom`, Proxcloud must place the
rendered `.yaml` on the datastore path (`/var/lib/vz/snippets/…` for `local`, or
the datastore's configured path) via **SSH/SFTP or a node-local writer**, *then*
reference it with `cicustom`. There is no API-only path. Order matters: the file
must exist on storage **before the VM starts** (cloud-init runs at first boot).

### 1.4 CRITICAL override semantics: `cicustom user=` wins; the snippet is authoritative

When `cicustom user=<vol>` is set, PVE's generated **user-data** is discarded and
your file is used verbatim. Consequently the inline user parameters are **ignored
for user-data**:

- `ciuser`, `cipassword`, and `sshkeys` **have no effect** on the login user once
  a custom `user=` file is in place. Thomas-Krenn: *"the cloud init parameters
  from the Proxmox VE Web UI no longer apply"* and *"the custom CI file always has
  priority."* The community consensus is identical: with a custom user snippet,
  **only the options set in the snippet are used**.

**Therefore the snippet MUST carry the login identity itself** — `users:`,
`ssh_authorized_keys:`, and (if a password is wanted) `chpasswd:` /
`hashed_passwd`. Do not rely on `ciuser`/`cipassword`/`sshkeys` alongside
`cicustom user=`; they are dead parameters in that mode.

> **Migration note for `params.go`:** today (`:225-234`) the qemu path sets
> `ciuser`/`cipassword`/`sshkeys`. When the catalog switches a service to a
> `cicustom user=` snippet, **drop those three** (they become no-ops) and move
> the identity into the snippet's `#cloud-config`. Keep the network/DNS params
> (`ipconfig0`, `nameserver`, `searchdomain`) — see §1.5.

### 1.5 The generated cloudinit drive is STILL required alongside `cicustom`

`cicustom` chooses the **content** of the cloud-init files; the **delivery
mechanism** is unchanged — PVE builds a small cloud-init image (NoCloud/
ConfigDrive) and attaches it as a CD-ROM. Cloud-Init Support wiki: *"all
Cloud-Init VMs need to have an assigned CD-ROM drive."* That drive is the one the
current code sets: `ide0=<storage>:cloudinit` (`params.go:224`). **Keep it.**
Without a `…:cloudinit` drive there is no datasource and the snippet is never
delivered.

How the parts combine on that one drive:

- `user=` → your snippet becomes the **user-data**.
- **network** → because we set only `user=`, PVE **still generates
  network-config from `ipconfig0`** (and `nameserver`/`searchdomain`). So static
  IP / DHCP continues to be driven by the existing `ipconfig0` logic
  (`params.go:241-250`) — do **not** move networking into the snippet unless you
  also switch to `cicustom network=`.
- `meta=` → generated (instance-id, hostname) unless you override it.

`citype` defaults correctly for us: schema says NoCloud for Linux
(*"We use the `nocloud` format for Linux, and `configdrive2` for windows"*), so
no explicit `citype` is needed for the Linux catalog images.

### 1.6 Concrete example

**Rendered snippet** placed at `local:snippets/svc-<vmid>.yaml` (via SSH, §1.3):

```yaml
#cloud-config
hostname: web-01
manage_etc_hosts: true

users:
  - name: proxcloud
    groups: [sudo]
    sudo: ALL=(ALL) NOPASSWD:ALL
    shell: /bin/bash
    lock_passwd: true
    ssh_authorized_keys:
      - ssh-ed25519 AAAAC3NzaC1lZDI1... user@host

package_update: true
packages:
  - qemu-guest-agent
  - nginx

runcmd:
  - [ systemctl, enable, --now, qemu-guest-agent ]
  - [ systemctl, enable, --now, nginx ]
```

**Exact `qm`/API params** (networking + drive stay inline; identity is in the
snippet):

```
# create (or qm set) — user-data comes from the snippet:
--ide0        local-lvm:cloudinit
--cicustom    "user=local:snippets/svc-<vmid>.yaml"
--ipconfig0   "ip=10.0.0.20/24,gw=10.0.0.1"     # still honored (network is generated)
--nameserver  "10.0.0.1"
--agent       1
# NOTE: no --ciuser/--cipassword/--sshkeys — they would be ignored (§1.4).
```

`qemu-guest-agent` in `packages:` + `--agent 1` is what makes readiness
detectable (§3). The snippet installs it; the config enables the virtio channel.

## 2. LXC — native provisioning, NOT a cloud-init datasource

**LXC does not use a cloud-init datasource the way VMs do.** There is no
`cicustom`, no cloudinit CD-ROM, and no `#cloud-config` user-data path for a
stock container template. `pct create` provisions the container by **mounting its
rootfs and editing files directly** via native parameters (`pct(1)`; schema
`/nodes/{node}/lxc` POST):

- `password` — "Sets root password inside container."
- `ssh-public-keys` — "Setup public SSH keys (one key per line, OpenSSH format)."
- `nameserver` — "Sets DNS server IP address for a container."
- `searchdomain` — "Sets DNS search domains for a container."

This is exactly what `params.go:196-209` already does. These are applied by PVE
directly to the container filesystem — **not** interpreted by cloud-init.

**Design decision (v1):** arbitrary `#cloud-config` **user-data
(`packages:`, `runcmd:`, `users:`, etc.) is a VM-only path.** Catalog services
that need package installs or first-boot scripting are deployed as **qemu VMs**
(§1). LXC in v1 gets only root password + SSH keys + DNS via the native params
above.

**Future LXC options (not wired in v1):**

1. **Post-create `pct exec`** (`POST /nodes/{node}/lxc/{vmid}/exec`, or
   `pct exec <vmid> -- …`) to run install/config steps after start. This runs on
   the node, not via a guest agent.
2. **A cloud-init-enabled container template** (some distro LXC images ship
   `cloud-init` with a NoCloud/`lxc` datasource). This requires a purpose-built
   template and is out of scope for the v1 catalog.

Either can be an ADR later; do not assume LXC user-data works today.

## 3. Guest-agent readiness / IP reporting ("configuring → ready")

### 3.1 The agent enables IP reporting

With `qemu-guest-agent` installed **and running** in the guest (the §1.6 snippet
does both) and `--agent 1` on the VM, PVE can query the guest over the virtio
channel:

- `GET /nodes/{node}/qemu/{vmid}/agent/network-get-interfaces` → the guest's
  interfaces and IP addresses. This is exactly what `AgentInterfaces`
  (`guest_config.go:126-163`) parses (`result[].ip-addresses[]`).

Until the agent answers, PVE returns HTTP 500 *"QEMU guest agent is not
running"* / *"No QEMU guest agent configured"* — which the code already maps to
`ErrAgentUnavailable` (`guest_config.go:139-144`). That error is the **honest
"not ready yet"** state, not a failure.

**Privileges (PVE 9.x — version-sensitive!).** Verbatim from the API schema
`check` blocks:

- `network-get-interfaces`:
  `["perm","/vms/{vmid}",["VM.GuestAgent.Audit","VM.GuestAgent.Unrestricted"],"any",1]`
  → needs **`VM.GuestAgent.Audit`** (or the stronger `.Unrestricted`).
- `agent/exec` and `agent/exec-status`:
  `["perm","/vms/{vmid}",["VM.GuestAgent.Unrestricted"]]` → needs
  **`VM.GuestAgent.Unrestricted`**.

> **Version flag:** PVE **9.x introduced the `VM.GuestAgent.*` privilege family**
> and split guest-agent access out of the old catch-all. On **PVE 8.x** these
> agent endpoints were gated by **`VM.Monitor`** instead. Since the server is
> **9.2.4**, grant `VM.GuestAgent.Audit` for read-only IP polling. If the token
> currently only has `VM.Monitor`, IP reporting will **fail on 9.x** (observed as
> *"Requires 'VM.Monitor' Privileges"* → now *GuestAgent*); update the ACL.

### 3.2 The readiness signal Proxcloud uses

**There is NO native "cloud-init finished" signal exposed over the PVE API.** The
only guest-introspection endpoints are the `agent/*` RPCs above; none reports
cloud-init phase. Proxcloud therefore infers readiness from **the guest OS having
booted far enough that the agent answers with a usable IP**:

- `configuring` → VM started, task `OK`, but `network-get-interfaces` returns
  `ErrAgentUnavailable` or no routable IPv4.
- `ready` → `network-get-interfaces` returns at least one non-loopback IPv4
  (the code already skips `lo`, `guest_config.go:149`).

Caveat: the agent can answer **before** cloud-init has finished `runcmd`/package
installs. An IP means "booted and networked," not "provisioning complete."

### 3.3 `agent/exec` exists but is NOT yet wired — future `cloud-init status --wait`

PVE does expose command execution over the agent:

- `POST /nodes/{node}/qemu/{vmid}/agent/exec` (returns a `pid`) +
  `GET /nodes/{node}/qemu/{vmid}/agent/exec-status?pid=<pid>` (`exited`,
  `exitcode`, `out-data`).

This *could* run `cloud-init status --wait` in-guest for a **true** "provisioning
complete" gate. **Proxcloud's client does not implement `exec`/`exec-status`
today** (only `network-get-interfaces` is wired). Treat exec-based completion as a
**future upgrade** — and note it needs the stronger `VM.GuestAgent.Unrestricted`
(§3.1) and the agent already running.

### 3.4 Recommended v1 readiness: port-probe

For v1, gate `ready` on a **port probe** rather than the agent alone:

1. Await the create/start task → `exitstatus: OK` (see `lifecycle.md` §2).
2. Poll `network-get-interfaces` until a routable IPv4 appears (needs
   `VM.GuestAgent.Audit`). Treat `ErrAgentUnavailable` as "keep waiting."
3. **TCP-probe** the service's expected port (e.g. 22, or the catalog service
   port) at that IP until it accepts a connection, with a bounded timeout.

Rationale: the port opening is a concrete "the service the user asked for is up"
signal that survives images without the agent and does not require
`VM.GuestAgent.Unrestricted`. Upgrade to `cloud-init status --wait` via
`agent/exec` when that client method lands.

## 4. Escaping / encoding pitfalls (SECURITY-CRITICAL)

Proxcloud renders snippets that contain **user-supplied or generated
credentials** (usernames, passwords, keys). These strings can legally contain
`" ' $ \` \ newline # : |` and `$(...)`. Injecting them raw is unsafe in **two**
distinct ways.

### 4.1 Why raw interpolation is unsafe

1. **YAML-structure breakage / injection.** A snippet is YAML. Interpolating a
   raw value into a scalar can terminate the string, inject new keys, or change
   the document. Characters that break or hijack YAML include `:` (mapping),
   `#` (comment), `"`/`'` (quote termination), `|`/`>` (block scalars), leading
   `-`/`?`, and newlines (a `\n` in a password can inject an entire new YAML
   line, e.g. a second `runcmd` step or an extra user).
2. **Shell injection in `runcmd`.** `runcmd:` entries are executed by a shell
   when written as a string. A value containing `$(…)`, backticks, `;`, `|`, or
   `&&` runs attacker-controlled commands **as root at first boot**. Even the
   list form `- [ cmd, arg ]` is unsafe if the value is concatenated into an
   `sh -c` string elsewhere.

Both mean: **never build YAML or shell text by string-concatenating a raw
credential.**

### 4.2 Unsafe example (do NOT do this)

```yaml
#cloud-config
users:
  - name: PROXCLOUD_USER            # e.g.  admin
chpasswd:
  list: |
    PROXCLOUD_USER:PROXCLOUD_PASS   # e.g.  admin:hunter2
runcmd:
  - echo "welcome PROXCLOUD_USER" > /etc/motd
```

If `PROXCLOUD_PASS` is `p:ss"word` the `chpasswd` line's structure breaks; if it
is `x\n  - name: root\n    ...` a whole new user is injected; if the motd value is
`$(rm -rf /)` the shell in `runcmd` executes it as root.

### 4.3 Safe method: base64-encode at render, decode in-guest

Encode each untrusted value to **base64 at render time** and place only the
base64 blob (which is `[A-Za-z0-9+/=]` — YAML- and shell-safe) into the snippet.
Decode it **in-guest** in a `runcmd`, so the raw bytes never touch YAML structure
or a shell parser:

```yaml
#cloud-config
package_update: true
packages:
  - qemu-guest-agent

# Only base64 blobs are interpolated. B64_USER / B64_PASS are the
# render-time base64 of the raw username/password. B64_SSHKEY is the key.
runcmd:
  - [ systemctl, enable, --now, qemu-guest-agent ]
  - |
    set -eu
    U="$(printf %s 'B64_USER' | base64 -d)"
    P="$(printf %s 'B64_PASS' | base64 -d)"
    id "$U" >/dev/null 2>&1 || useradd -m -s /bin/bash "$U"
    printf '%s:%s\n' "$U" "$P" | chpasswd
    install -d -m700 "/home/$U/.ssh"
    printf %s 'B64_SSHKEY' | base64 -d > "/home/$U/.ssh/authorized_keys"
    chmod 600 "/home/$U/.ssh/authorized_keys"
    chown -R "$U:$U" "/home/$U/.ssh"
```

Why this is safe:

- The base64 alphabet contains **no YAML metacharacters and no shell
  metacharacters**, so the interpolated token cannot break the document or the
  command line regardless of the underlying bytes.
- The single-quoted `'B64_…'` argument to `printf` is passed literally to
  `base64 -d`; the decoded raw value only ever exists as the value of a shell
  variable (`"$U"`, `"$P"`) and is always used **double-quoted**, so word-
  splitting and re-globbing cannot re-inject it.
- The raw password is never written to YAML, never appears in `chpasswd:` YAML
  structure, and never lands in a log line built by concatenation.

Prefer, where possible, **not** setting a password at all (SSH keys only, as the
prod template does with `lock_passwd: true`). When a password is unavoidable,
supply a **pre-hashed** value (`chpasswd: { list: "user:$6$…" }` with
`hashed_passwd`) — still base64-encoded through the pipeline above — so the
plaintext never transits the snippet.

> The same rule applies to **any** value that reaches PVE params, not just the
> snippet: `sshkeys` on the qemu config is declared **`urlencoded`** in the API
> schema, which is why `params.go:233` already `url.QueryEscape`s it. Keep that.

## 5. Required token privileges (least privilege)

On the guest path (`/vms/{vmid}`; grantable via pool or per-VM ACL). All privilege
strings below are quoted from the API schema `permissions`/`check` blocks.

| Action | Privilege(s) | Source (schema block) |
|--------|--------------|------------------------|
| Create qemu VM (with cloud-init drive + `cicustom` inline) | `VM.Allocate` on `/vms/{vmid}` or `/pool/{pool}`; `Datastore.AllocateSpace` on storage; `SDN.Use` on the bridge | `POST /nodes/{node}/qemu` |
| Set/replace `cicustom` post-create (config PUT/POST) | `VM.Config.Cloudinit` (any-of `VM.Config.{Disk,CDROM,CPU,Memory,Network,HWType,Options,Cloudinit}`) | `PUT /nodes/{node}/qemu/{vmid}/config` |
| Read VM config (verify cloud-init applied) | `VM.Audit` | `GET .../config` |
| Read guest IPs (`network-get-interfaces`) | `VM.GuestAgent.Audit` **or** `VM.GuestAgent.Unrestricted` | `GET .../agent/network-get-interfaces` |
| Run `agent/exec` + read `exec-status` (future §3.3) | `VM.GuestAgent.Unrestricted` | `POST .../agent/exec`, `GET .../agent/exec-status` |
| Create LXC (native provisioning) | `VM.Allocate`; `Datastore.AllocateSpace`; `Sys.Modify` on `/` only for **privileged** containers (Proxcloud uses `unprivileged=1`, so not needed) | `POST /nodes/{node}/lxc` |

### `pveum` setup — cloud-init + readiness role (PVE 9.x)

```bash
# Create + cloud-init config + read IPs (read-only agent), least privilege.
pveum role add ProxcloudProvision -privs \
  "VM.Allocate VM.Config.Cloudinit VM.Audit VM.GuestAgent.Audit"

# Grant to the API token, scoped to the Proxcloud pool (preferred):
pveum acl modify /pool/proxcloud -token 'proxcloud@pam!provision' -role ProxcloudProvision

# Storage rights (disk + snippet datastore) — AllocateSpace is enough to place
# disks; snippet FILE placement is over SSH (§1.3), not an API privilege.
pveum acl modify /storage/<diskstore>    -token 'proxcloud@pam!provision' -role PVEDatastoreUser
pveum acl modify /storage/<snippetstore> -token 'proxcloud@pam!provision' -role PVEDatastoreUser

# Bridge/VLAN (SDN) use, if the create sets net0 on a managed bridge:
pveum acl modify /sdn/zones/localnetwork -token 'proxcloud@pam!provision' -role PVESDNUser

# ONLY if a future feature needs cloud-init-status via agent exec:
# pveum role add ProxcloudExec -privs "VM.GuestAgent.Unrestricted"
# pveum acl modify /pool/proxcloud -token 'proxcloud@pam!provision' -role ProxcloudExec
```

Notes:
- **Token privilege separation** is on by default — the ACL must be applied to the
  **token**, not just the owning user (see `lifecycle.md` §6).
- Do **not** grant `VM.GuestAgent.Unrestricted` for v1: read-only IP polling only
  needs `.Audit`. Reserve `.Unrestricted` for the exec-based readiness upgrade.
- **`cicustom` and the snippet-storage caveat:** setting `cicustom` to a
  **volume-id** (`store:snippets/f.yaml`) requires only `VM.Config.Cloudinit` on
  the VM — no extra API privilege on the snippet content. There is a known
  security caveat that **snippet storage is not pool-scoped**, so any principal
  who can edit a VM's config can attach *any* snippet file that exists on a
  visible snippets store. Passing an **absolute filesystem path** (not a
  volume-id) to `cicustom` is **root-only**. Proxcloud must therefore (a) always
  use the volume-id form, and (b) treat the snippets datastore as trusted/isolated
  to Proxcloud. **Verify on the real 9.2.4 server** whether the scoped token can
  set `cicustom` without root before shipping (§6).

   ```bash
   curl -sk -H "$AUTH" "$PVE/nodes/$N/qemu/$V/agent/network-get-interfaces" \
     | jq '.data.result[]?.["ip-addresses"]'
   ```
4. **Override behavior sanity check.** After setting `cicustom user=`, dump the
   effective cloud-init and confirm `ciuser`/`sshkeys` are absent from user-data
   while `ipconfig0` still shapes network-config:
   ```bash
   qm cloudinit dump <vmid> user     # should be your snippet, verbatim
   qm cloudinit dump <vmid> network  # should reflect ipconfig0, still generated
   ```

## What this means for the backend (catalog wave)

Recommended qemu provisioning sequence (identity in snippet, network inline):

1. **Render** the `#cloud-config` snippet; **base64-encode every untrusted
   credential** and decode in `runcmd` (§4.3). Never concatenate raw values into
   YAML or shell.
2. **Place** the snippet on a `snippets`-enabled datastore via SSH/SFTP (§1.3) —
   there is no REST upload. File must exist before first boot.
3. **Create** the VM with `ide0=<store>:cloudinit`, `cicustom
   "user=<store>:snippets/<f>.yaml"`, `ipconfig0`, `nameserver`, `agent=1`, and
   **omit** `ciuser`/`cipassword`/`sshkeys` (§1.4). Await the create task
   (`exitstatus: OK`, see `lifecycle.md` §2).
4. **Start**, then poll `network-get-interfaces` (needs `VM.GuestAgent.Audit`) for
   a routable IPv4; treat `ErrAgentUnavailable` as "still configuring" (§3.2).
5. **Gate `ready`** on a TCP port probe of the service port at that IP (§3.4).
   Future: replace with `cloud-init status --wait` via `agent/exec`
   (`VM.GuestAgent.Unrestricted`, §3.3).
6. **LXC** stays on native params (`password`, `ssh-public-keys`, `nameserver`);
   no `#cloud-config`. Package/first-boot needs → deploy as a VM (§2).
